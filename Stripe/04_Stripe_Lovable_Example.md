# **Stripe Payment Integration with Spring Boot – Lovable Clone**

We are replacing the previous e-commerce mouse example with your actual **Lovable Clone subscription payment implementation**.

The main difference:

- Previous example: Customer purchases a product once (₹500).
- Your project: User subscribes to a plan (monthly/recurring subscription).

We will follow your actual code, explain the purpose of each important method, and connect everything through one continuous flow.

# **1. Understand the complete integration first**

Suppose your Lovable Clone offers three subscription plans:

| Plan    | Price      | Features           |
| ------- | ---------- | ------------------ |
| Free    | ₹0         | 1 project          |
| Pro     | ₹499/month | 10 projects        |
| Premium | ₹999/month | Unlimited projects |

A user selects the Pro plan.

What happens?

1. We create the Pro product and its recurring price in Stripe.
2. Stripe generates a unique Price ID.
3. We store that Stripe Price ID in our `Plan` table.
4. User selects the Pro plan on our frontend.
5. Frontend sends the selected `planId` to Spring Boot.
6. Backend identifies the logged-in user.
7. Backend fetches the selected plan from the database.
8. Backend uses the stored Stripe Price ID to create a Checkout Session.
9. Stripe returns a Checkout URL.
10. Frontend redirects the user to Stripe.
11. User completes the subscription payment.
12. Stripe sends a webhook event to our backend.
13. Backend verifies the event and activates the user's subscription.
14. User gets access to the features included in the Pro plan.

**Remember this important concept:**

We don't create a new Stripe product every time a user subscribes.

We create products and prices in Stripe beforehand. Users select our locally stored plans, and we use their associated Stripe Price IDs during checkout.

# **2. Important Stripe concepts used in your project**

## **2.1 Product and Price**

Stripe has two important concepts:

**Product:** What are we selling?

Example: Lovable Pro Plan.

**Price:** How much does it cost, and how frequently does the customer pay?

Example: ₹499 per month.

**Stripe Dashboard**

Product

**Lovable Pro**

Product ID: prod_ABC123

**Recurring Price**

# **₹499/month**

Price ID: price_XYZ789

We save the Price ID in our database

**Our Plan table**

| id | name | stripePriceId |
| -- | ---- | ------------- |
| 2  | Pro  | price_XYZ789  |

### **Why do we store the Stripe Price ID?**

Because when a user selects Pro, our backend needs to tell Stripe exactly which price the user wants to purchase.

We don't send ₹499 from the frontend.

We fetch the plan from our database and retrieve its `stripePriceId`.

Your entity:

```
@Entity
public class Plan {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    Long id;

    String name;

    @Column(unique = true)
    String stripePriceId;

    Integer maxProjects;
    Integer maxTokensPerDay;
    Integer maxPreviews;

    Boolean unlimitedAi;
    Boolean active;
}
```

**Understand these fields:**

| Field             | Purpose                       |
| ----------------- | ----------------------------- |
| `id`              | Our internal plan ID          |
| `name`            | Plan name, e.g. Pro           |
| `stripePriceId`   | Unique Stripe Price ID        |
| `maxProjects`     | Maximum projects allowed      |
| `maxTokensPerDay` | Daily AI token limit          |
| `maxPreviews`     | Preview limit                 |
| `unlimitedAi`     | Whether AI usage is unlimited |
| `active`          | Whether the plan is available |

Notice that we have two different IDs:

- `Plan.id` → Generated by our database.
- `stripePriceId` → Generated by Stripe.

They identify the same subscription plan in two different systems.

## **2.2 Customer**

A Customer represents a user in Stripe.

Suppose a user registers in our Lovable Clone.

We have:

- Our database user ID: `101`
- Username/email: `user@gmail.com`
- Stripe Customer ID: `cus_ABC123`

We store the Stripe Customer ID in our User table.

Why?

So that Stripe can recognize the same customer during future payments, subscription renewals, and customer portal operations.

Your code uses:

```
String stripeCustomerId = user.getStripeCustomerId();
```

If the user already has a Stripe Customer ID, we reuse it.

Otherwise, we provide their email address during Checkout Session creation.

Later, Stripe returns the Customer ID, and we save it in our database.

## **2.3 Checkout Session**

A Checkout Session represents one checkout process.

In your project:

- User selects Pro.
- Backend creates a Checkout Session.
- Stripe returns a Checkout URL.
- User opens the Stripe-hosted payment page.

Your code creates this using:

```
Session session = Session.create(params.build());
```

The important thing: A Checkout Session is not the same as a Subscription.

The session handles the checkout process. The subscription represents the recurring billing relationship.

## **2.4 Subscription**

A Subscription represents the recurring payment relationship between the user and your application.

For example:

User subscribes to Pro for ₹499/month.

Stripe manages the recurring billing cycle.

Your application stores information such as:

- User ID
- Plan ID
- Stripe Subscription ID
- Stripe Customer ID
- Subscription status
- Current billing period

Your `SubscriptionService` is responsible for updating this information.

## **2.5 Webhook**

A webhook is an HTTP request sent by Stripe to our backend when something happens.

For example:

- User completes checkout.
- Subscription gets updated.
- Subscription gets cancelled.
- Invoice gets paid.
- Payment fails.

**Why do we need it?**

Because the frontend success page cannot reliably confirm whether a payment was successful.

Stripe communicates the actual event to our backend through webhooks.

# **5. Webhook Integration – Most important part**

Now comes the second half of the integration.

The user has completed checkout.

But how does our backend know that?

Stripe sends a webhook request to our application.

Your endpoint:

```
@PostMapping("/webhooks/payment")
public ResponseEntity<String> handlePaymentWebhooks(
        @RequestBody String payload,
        @RequestHeader("Stripe-Signature") String sigHeader)
```

### **5.1 Receive webhook request**

Two important parameters:

| Parameter   | Purpose                       |
| ----------- | ----------------------------- |
| `payload`   | Raw JSON event sent by Stripe |
| `sigHeader` | Signature sent by Stripe      |

Example event type:

```
checkout.session.completed
```

### **5.2 Verify webhook signature**

```
Event event = Webhook.constructEvent(
    payload,
    sigHeader,
    webhookSecret
);
```

Why do we verify it?

Because we must ensure that the webhook actually came from Stripe and was not forged by someone else.

- `payload` → Event data.
- `sigHeader` → Stripe signature.
- `webhookSecret` → Our endpoint's secret used to verify the signature.

If the signature is invalid, we return:

```
HttpStatus.BAD_REQUEST
```

**Remember:** Never trust a webhook without verifying its signature.

### **5.3 Deserialize webhook event**

```
EventDataObjectDeserializer deserializer =
    event.getDataObjectDeserializer();

StripeObject stripeObject = null;

if (deserializer.getObject().isPresent()) {
    stripeObject = deserializer.getObject().get();
}
```

What is happening?

Stripe sends event data in JSON format.

We need to convert that JSON into the appropriate Java object.

For example:

- Checkout Session event → `Session`
- Subscription event → `Subscription`
- Invoice event → `Invoice`

Your code also includes a fallback:

```
stripeObject = deserializer.deserializeUnsafe();
```

This attempts to deserialize the object even when the normal deserialization path cannot provide it.

## **6.2 customer.subscription.updated**

Your method:

```
private void handleCustomerSubscriptionUpdated(
        Subscription subscription) {

    if (subscription == null) {
        log.error("subscription object was null");
        return;
    }

    SubscriptionStatus status =
        mapStripeStatusToEnum(subscription.getStatus());

    if (status == null) {
        return;
    }

    SubscriptionItem item =
        subscription.getItems().getData().get(0);

    Instant periodStart =
        toInstant(item.getCurrentPeriodStart());

    Instant periodEnd =
        toInstant(item.getCurrentPeriodEnd());

        subscription.getId(),
        status,
        periodStart,
        periodEnd,
        subscription.getCancelAtPeriodEnd(),

}
```

```
private SubscriptionStatus mapStripeStatusToEnum(
        String status) {

    return switch(status) {
        case "active" -> SubscriptionStatus.ACTIVE;
        case "trialing" -> SubscriptionStatus.TRIALING;

        case "past_due", "unpaid", "paused" ->
            SubscriptionStatus.PAST_DUE;

        case "canceled" -> SubscriptionStatus.CANCELED;
        case "incomplete" -> SubscriptionStatus.INCOMPLETE;

        default -> null;
    };
}
```

Why?

We convert Stripe's status into our application's status.

```
private Long resolvePlanId(Price price) {

    if (price == null || price.getId() == null)
        return null;

    return planRepository.findByStripePriceId(price.getId())
        .map(Plan::getId)
        .orElse(null);
}
```

# **9. Complete Stripe integration revision**

Remember this flow

This is the entire integration in one place.

**Phase 1 – Initial setup**

1. &#x20;Create Product in Stripe.
2. &#x20;Create recurring Price in Stripe.
3. &#x20;Get the unique Stripe Price ID.
4. &#x20;Store Stripe Price ID in our Plan table.
5. &#x20;Store Stripe Customer ID in User table when available.

**Phase 2 – Checkout**

1. &#x20;User selects a plan.
2. Frontend sends `planId`.
3. &#x20;BillingController receives the request.
4. &#x20;StripePaymentProcessor fetches User and Plan.
5. &#x20;Creates Checkout Session using Stripe Price ID.
6. &#x20;Stripe returns Checkout URL.
7. &#x20;Frontend redirects user to Stripe.

**Phase 3 – Webhook**

1. &#x20;User completes checkout.
2. &#x20;Stripe sends webhook.
3. &#x20;BillingController verifies signature.
4. &#x20;Extracts Stripe event and metadata.
5. &#x20;StripePaymentProcessor identifies event type.
6. &#x20;SubscriptionService activates or updates subscription.
7. &#x20;Database stores the latest subscription information.

# **Final understanding**

There are only three major things you need to understand deeply:

**1. Product and Price**

We create products and recurring prices in Stripe, get the unique Price ID, and store that ID in our database.

**2. Checkout Session**

User selects a plan → Backend fetches the plan → Uses Stripe Price ID → Creates Checkout Session → Returns URL → Frontend redirects to Stripe.

**3. Webhook**

Stripe sends an event → Backend verifies it → Identifies the user and subscription → SubscriptionService updates our database.

If you understand these three flows and how your `BillingController`, `StripePaymentProcessor`, and `SubscriptionService` communicate, you understand the foundation of Stripe subscription integration.
