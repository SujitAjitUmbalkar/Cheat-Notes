# Kafka Notes – Part 1 : Why Kafka?

## 1. Why do we need Kafka?

In a distributed microservices architecture, services communicate with each other.

Initially, communication is usually done using:

* RestClient
* OpenFeign

These use **HTTP Request-Response Communication**.

```text
Service A
    │
HTTP Request
    │
    ▼
Service B
```

Service A sends a request and **waits** until Service B returns a response.

This is called **Synchronous Communication**.

---

# Problems with Request-Response Communication

## 1. Tight Coupling

Service A depends on Service B.

If Service B is unavailable, slow, or crashes,

Service A cannot continue its work.

```text
Service A
    │
    ▼
Service B ❌

↓

Request Failed
```

---

## 2. Poor Scalability

Suppose an Order Service calls:

* Payment Service
* Inventory Service
* Notification Service
* Shipping Service

For every order, four HTTP requests are generated.

If thousands or millions of orders arrive, the number of HTTP requests increases rapidly, making the system harder to scale. 

---

## 3. Fault Tolerance

If a target service is down,

the HTTP request fails.

Without additional mechanisms (Retry, Circuit Breaker, etc.), the work may fail.

---

## 4. Large Data Streams

Modern applications continuously generate huge amounts of data such as:

* Orders
* Payments
* User Logins
* Inventory Updates
* Notifications

Traditional request-response communication is not ideal for processing these continuous event streams. 

---

# Does Kafka Replace OpenFeign or RestClient?

**No.**

They solve different problems.

| OpenFeign / RestClient      | Kafka                           |
| --------------------------- | ------------------------------- |
| HTTP Communication          | Event Streaming Platform        |
| Request → Response          | Publish → Consume               |
| Synchronous                 | Asynchronous                    |
| Waits for response          | Doesn't wait for processing     |
| Immediate response required | Immediate response not required |

---

# OpenFeign Flow

```text
Order Service
      │
HTTP Request
      │
      ▼
Inventory Service

↓

Response Returned

↓

Order Service Continues
```

Order Service waits until Inventory Service responds.

---

# Kafka Flow

```text
Order Service

      │

Publish Event

      │

      ▼

    Kafka

      │

      ▼

Inventory Service
```

Order Service publishes an event to Kafka and continues its own work.

It does **not** wait for Inventory Service.

---

# Why Kafka Works Even If a Service Is Down

Kafka stores published events.

If a consumer service is unavailable,

the event remains stored in Kafka.

When the service comes back,

it can read the stored event and continue processing according to Kafka's retention and offset mechanisms. 

---

# Phone Call vs Post Office

### OpenFeign / RestClient

Like making a phone call.

```text
You

↓

Call Friend

↓

Friend Doesn't Answer

↓

Call Failed
```

---

### Kafka

Like sending a parcel through a post office.

```text
You

↓

Post Office

↓

Friend Not Home

↓

Parcel Stored

↓

Friend Receives Later
```

Kafka acts like the post office.

---

# What is an Event?

An **event** is a piece of data that represents **something that has already happened**.

It is **not a command**.

Examples:

* UserRegistered
* OrderPlaced
* PaymentCompleted
* InventoryUpdated
* OrderCancelled
* EmailSent

Notice that event names are generally written in **past tense** because they describe completed facts.

---

# Event Example

When an order is placed,

Order Service creates an event.

```json
{
  "orderId": 101,
  "customerId": 25,
  "productId": 50,
  "quantity": 2
}
```

This event is published to Kafka.

It is simply data describing what happened.

---

# Event Flow

```text
Customer Places Order
          │
          ▼
Order Service
(Saves Order in Database)
          │
          ▼
Creates OrderPlaced Event
          │
          ▼
Publishes Event to Kafka
```

---

# Multiple Services Can Use One Event

```text
                Kafka
                  │
      --------------------------
      │        │        │      │
Inventory  Payment  Email  Analytics
 Service    Service Service Service
```

One published event can be consumed by multiple interested services.

The producer does not need to know who consumes it.

This decouples producers and consumers, one of Kafka's main goals. 

---

# Producer's Responsibility

The producer (e.g., Order Service) only announces:

> **"An Order has been placed."**

It does **not** decide:

* Who should receive it.
* How many services should process it.
* When they should process it.

Each consumer decides independently.

---

# Interview Points

### What is an Event?

> An event is a piece of data representing something that has already happened in the system.

---

### Why use Kafka instead of OpenFeign?

> Kafka enables asynchronous communication, stores events, reduces coupling between services, and allows independent processing, whereas OpenFeign is synchronous and requires an immediate response.

---

### Difference Between Command and Event

| Command                | Event                       |
| ---------------------- | --------------------------- |
| Do this                | This happened               |
| Future action          | Past occurrence             |
| Example: `MakePayment` | Example: `PaymentCompleted` |
