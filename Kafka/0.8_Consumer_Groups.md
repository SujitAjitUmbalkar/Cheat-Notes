
# Concept 8 – Consumer Groups

This concept has these subtopics:

# Subtopic 1 – Why do we need Consumer Groups?

Suppose we have:

```text
orders Topic

├── Partition 0
├── Partition 1
└── Partition 2
```

One Inventory Consumer is running.

```text
Inventory Consumer

↓

Reads P0

Reads P1

Reads P2
```

Suppose:

* Consumer can process **100 events/sec**
* Producer sends **1000 events/sec**

Result:

```text
New Events

↓

Kafka

↓

Partition

↓

Consumer (Too Slow)

↓

Events Keep Increasing
```

The consumer cannot keep up.

We need more processing power.

---

# Subtopic 2 – What is a Consumer Group?

Instead of one Inventory Consumer,

we start multiple instances.

```text
Inventory Service

Instance 1

Instance 2

Instance 3
```

All belong to the same group.

Example:

```properties
group.id=inventory-group
```

Kafka now treats them as one team.

```text
inventory-group

├── Consumer A
├── Consumer B
└── Consumer C
```

This team is called a **Consumer Group**.

### Definition

> **A Consumer Group is a collection of consumers that work together to consume a topic in parallel.**

# Subtopic 3 – How Kafka Assigns Partitions

Suppose

```text
orders

├── P0
├── P1
├── P2
```

Consumers:

```text
Consumer A

Consumer B
```

Kafka assigns:

```text
Consumer A

↓

P0

P2
```

```text
Consumer B

↓

P1
```

Notice:

Kafka decides the assignment.

You don't manually assign partitions in the common case.

---

# Subtopic 4 – Rules of Consumer Groups ⭐⭐⭐

## Rule 1

One partition is assigned to only **one consumer** within the same consumer group.

Correct:

```text
P0 → Consumer A

P1 → Consumer B
```

Wrong:

```text
P0 → Consumer A

P0 → Consumer B
```

That would cause duplicate processing.

---

## Rule 2

One consumer **can** consume multiple partitions.

Example:

```text
Consumer A

↓

P0

P2
```

Perfectly valid.

---

## Rule 3

A partition cannot be shared by two consumers in the same group.

Kafka never allows this.

---

# Subtopic 5 – Scaling

Initially:

```text
inventory-group

Consumer A
```

Later, traffic increases.

You start:

```text
Consumer B
```

Now Kafka redistributes the work.

Instead of one consumer doing everything,

both consumers process events in parallel.

This is called **horizontal scaling**.

# Subtopic 6 – Common Scenarios

## Scenario 1

### 3 Partitions, 3 Consumers

```text
P0 → Consumer A

P1 → Consumer B

P2 → Consumer C
```

Perfect balance.

---

## Scenario 2

### 3 Partitions, 2 Consumers

```text
Consumer A

↓

P0

P2
```

```text
Consumer B

↓

P1
```

One consumer owns two partitions.

Valid.

---

## Scenario 3

### 3 Partitions, 1 Consumer

```text
Consumer A

↓

P0

P1

P2
```

Also valid.

---

## Scenario 4 ⭐⭐⭐

### 3 Partitions, 5 Consumers

```text
P0 → Consumer A

P1 → Consumer B

P2 → Consumer C

Consumer D → Idle

Consumer E → Idle
```

Kafka cannot assign more than one consumer to the same partition within a group.

So extra consumers simply wait.

# Summary

```text
Consumer Group

↓

Consumers work as a team

↓

Kafka assigns partitions

↓

One partition → One consumer

↓

One consumer → Multiple partitions (possible)

↓

More consumers = Better parallel processing
```

---

# Remember

* Consumer Group = Team of consumers.
* Consumers in the same group share the work.
* Kafka automatically assigns partitions.
* One partition belongs to only one consumer in a group.
* One consumer may own multiple partitions.
* If consumers > partitions, extra consumers remain idle.
* If partitions > consumers, some consumers handle multiple partitions.

* Consumers in the same Consumer Group divide the work among themselves, so each message is processed only once by that group.
* Each record is processed only once within a Consumer Group.
* Kafka prevents duplicate processing by assigning a partition to only one consumer in the group.

### Small clarification 

The phrase "processed only once" is with respect to normal consumption in a consumer group.

It does not mean Kafka can never deliver a message again. Under failures, retries, or manual offset changes, the same record may be read again. We'll study those cases later when we learn delivery guarantees (at-most-once, at-least-once, exactly-once). Don't add this to your notes yet—we'll cover it in the appropriate section.
