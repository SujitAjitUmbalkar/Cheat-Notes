### Replication

```text
• Replication means keeping copies of the same partition on multiple brokers.
• Kafka replicates Partitions, not Topics.
• Each copy of a partition is called a Replica.
• Replication provides fault tolerance and high availability.
• If one broker fails, another broker with a replica can continue serving data.
```


# Why Replication?

Suppose your Kafka Cluster has only **one Broker**.

```text
Kafka Cluster

┌──────────────┐
│   Broker 1   │
│              │
│ orders-P0    │
└──────────────┘
```

Now imagine:

* Hard disk fails.
* Server crashes.
* Power failure.

What happens?

```text
Broker 1

❌ Down
```

Question:

Where are the events?

They are gone.

That means:

* Orders are lost.
* Payments are lost.
* Notifications are lost.

This is unacceptable in production.

So Kafka introduces **Replication**.

---

# Definition

> **Replication means keeping copies of the same partition on multiple brokers.**

Notice the wording.

Kafka replicates **Partitions**, **not Topics**.

---

# Example

Suppose Topic:

```text
orders

↓

Partition 0
```

Instead of storing it only on Broker 1,

Kafka stores copies.

```text
Broker 1

orders-P0
```

```text
Broker 2

orders-P0 (Copy)
```

```text
Broker 3

orders-P0 (Copy)
```

Now there are three copies of the same partition.

---

# Why only Partitions?

Remember:

A Topic is just a logical name.

Actual data lives inside partitions.

Therefore Kafka replicates **Partitions**.

Never Topics.

---

```text

```

Copies still exist.

```text

Broker 3 ✅
```

Kafka continues serving data.

No data loss.

No application failure.

### Doubt Note

* A broker can store **multiple partitions of the same topic**, including its own partition and replica partitions of other brokers.
* If a broker fails, Kafka promotes a replica on another broker to become the **Leader**.
* The new leader broker **serves** that partition to consumers.
* **Brokers do not process events**; they only **store and serve** partitions. **Consumers** read the events and execute the business logic.

# Leader & Follower Replica

### Notes

* Kafka replicates **Partitions**, not Topics.
* All replicas are **equal copies** of the same partition.
* Kafka elects **one replica** as the **Leader Replica**.
* The remaining replicas become **Follower Replicas**.
* Producers write data **only to the Leader Replica**.
* Consumers read data **only from the Leader Replica**.
* Follower Replicas continuously copy data from the Leader to stay synchronized.
* If the Leader fails, Kafka automatically promotes one of the Followers as the new Leader.

---

## Doubts Solved

* There is **no separate Master Partition** in Kafka.
* The **Leader Replica itself is the main (active) replica**.
* Leader and Followers are **roles**, not different types of partitions.
* A replica that is a Follower today can become the Leader if the current Leader fails.
* Producers never write directly to Follower Replicas.

---

## Remember ⭐

* **Partition** = Actual data.
* **Replica** = Copy of a partition.
* **Leader** = One of the replicas that is currently active for reads and writes.
* **Follower** = Replica that only copies data from the Leader.
* **Leader is not permanent**; it can change after broker failures.
* **There is no hidden "Master Partition" behind the Leader.** The Leader is simply one of the partition replicas chosen to serve client requests.

---

## What is Replication Factor?

**Replication Factor (RF)** specifies **how many replicas of each partition Kafka should maintain.**

Formula:

```text
Replication Factor = Total number of replicas of a partition
```

This count **includes the Leader Replica**.

---

## RF = 1

```text
orders Topic

P0

↓

Broker 1

P0 (Leader)
```

Replicas = 1

* Leader = 1
* Followers = 0

If Broker 1 crashes,

❌ Partition is lost.

---

## RF = 2

```text
Broker 1

P0 (Leader)
```

```text
Broker 2

P0 (Follower)
```

Replicas = 2

* Leader = 1
* Follower = 1

If Broker 1 crashes,

Kafka promotes Broker 2 as Leader.

System continues working.

---

## RF = 3

```text
Broker 1

P0 (Leader)
```

```text
Broker 2

P0 (Follower)
```

```text
Broker 3

P0 (Follower)
```

Replicas = 3

* Leader = 1
* Followers = 2

If one broker crashes,

another replica becomes Leader.

Kafka continues serving requests.

---

# Important Rule

Replication Factor **cannot be greater than the number of Brokers.**

Example:

```text
3 Brokers

RF = 5
```

❌ Impossible.

Kafka cannot create 5 replicas on only 3 brokers.

---

## Broker Failure Tolerance

| Replication Factor |                     Maximum Broker Failures (while still keeping a copy available) |
| ------------------ | ---------------------------------------------------------------------------------: |
| RF = 1             |                                                                                  0 |
| RF = 2             |                                                                                  1 |
| RF = 3             | Up to 2 (provided at least one in-sync replica remains available to become Leader) |

> In practice, whether the cluster continues to accept writes also depends on Kafka's configuration and which replicas are still in sync.

---

## Real Example

Suppose

```text
3 Brokers

RF = 3
```

```text
Broker 1

Leader
```

```text
Broker 2

Follower
```

```text
Broker 3

Follower
```

Producer writes

```text
OrderPlaced
```

Leader stores it.

Followers copy it.

If Broker 1 crashes,

Broker 2 becomes Leader.

Producer now writes to Broker 2.

Consumers also read from Broker 2.

No code changes.

Everything is automatic.

---

# Doubts Solved

* **Replication Factor counts the Leader Replica too.**
* RF = Total Replicas (Leader + Followers).
* Increasing RF increases fault tolerance but also uses more storage.
* Every partition of a topic has the same configured Replication Factor when the topic is created.

---

# Remember ⭐

* **RF = Number of replicas of each partition.**
* **Leader is included in the Replication Factor.**
* **RF cannot exceed the number of Brokers.**
* Higher RF provides higher availability and better fault tolerance.
* Replication is configured **per topic**, and Kafka applies it to each partition of that topic.

# Concept – In-Sync Replicas (ISR)

## What is ISR?

Not every Follower is always up to date.

Example:

```text
Leader

Offset 0
Offset 1
Offset 2
Offset 3
```

Follower A

```text
Offset 0
Offset 1
Offset 2
Offset 3
```

Follower B

```text
Offset 0
Offset 1
```

Follower B is behind.

Kafka creates a set called **ISR (In-Sync Replicas).**

ISR contains replicas that are **caught up** (or sufficiently caught up) with the Leader.

Example:

```text
ISR

Leader
Follower A
```

Follower B is **not** in ISR because it is lagging.

---

## Why ISR?

If the Leader crashes,

Kafka should promote only a replica that has the latest data.

Therefore,

Kafka elects the new Leader **from the ISR**.

---

## Notes

* ISR = In-Sync Replicas.
* ISR contains replicas synchronized with the Leader.
* Kafka elects the new Leader from the ISR.
* A lagging follower is removed from the ISR until it catches up.

---

# Concept – Leader Election

Suppose

```text
Broker 1

Leader
```

```text
Broker 2

Follower
```

```text
Broker 3

Follower
```

Leader crashes.

```text
Broker 1 ❌
```

Kafka immediately checks the ISR.

Example:

```text
ISR

Broker 2
Broker 3
```

Kafka chooses one.

```text
Broker 2

Leader
```

```text
Broker 3

Follower
```

Consumers automatically start reading from the new Leader.

Producers automatically start writing to the new Leader.

No code changes are required.

---

## Notes

* Leader Election occurs when the current Leader fails.
* Kafka selects the new Leader from the ISR.
* Producers and Consumers automatically communicate with the new Leader.
* Leader Election is automatic.

---

# Concept – Replica Synchronization

Producer sends

```text
OrderPlaced
```

Producer writes

```text
Leader
```

Leader stores the event.

Followers continuously fetch the latest data from the Leader.

Eventually,

```text
Leader

Offset 10
```

```text
Follower A

Offset 10
```

```text
Follower B

Offset 10
```

All replicas become synchronized.

---

## Notes

* Followers continuously copy data from the Leader.
* Replicas stay synchronized by fetching new records from the Leader.
* Synchronization ensures replicas are ready to become the Leader if needed.

---

# Concept – Fault Tolerance

Replication provides fault tolerance.

Example:

```text
RF = 3

Leader

Follower

Follower
```

If one broker fails,

Kafka elects another Leader.

Applications continue working.

Users usually don't notice the broker failure.

---

## Notes

* Replication provides High Availability.
* Replication prevents data loss during broker failures.
* Leader Election allows Kafka to continue serving Producers and Consumers.

---

# Remember ⭐

* **Partition** = Actual data.
* **Replica** = Copy of a partition.
* **Leader** = Active replica for reads and writes.
* **Follower** = Keeps itself synchronized with the Leader.
* **ISR** = Healthy replicas that are synchronized with the Leader.
* **Leader Election** = Kafka promotes a replica from the ISR when the Leader fails.
* **Replication Factor** = Total replicas (Leader + Followers).
* **Higher RF = Better fault tolerance but more storage usage.**
