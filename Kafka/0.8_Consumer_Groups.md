
# Concept 8 – Consumer Groups

This concept has these subtopics:

We'll complete all of these before moving to Rebalancing.

# Subtopic 1 – Why do we need Consumer Groups?

Suppose we have:

```text
orders Topic

├── Partition 0
├── Partition 1
└── Partition 2
```

One Inventory Consumer is running.

```text
Inventory Consumer

↓

Reads P0

Reads P1

Reads P2
```

Suppose:

* Consumer can process **100 events/sec**
* Producer sends **1000 events/sec**

Result:

```text
New Events

↓

Kafka

↓

Partition

↓

Consumer (Too Slow)

↓

Events Keep Increasing
```

The consumer cannot keep up.

We need more processing power.

---

# Subtopic 2 – What is a Consumer Group?

Instead of one Inventory Consumer,

we start multiple instances.

```text
Inventory Service

Instance 1

Instance 2

Instance 3
```

All belong to the same group.

Example:

```properties
group.id=inventory-group
```

Kafka now treats them as one team.

```text
inventory-group

├── Consumer A
├── Consumer B
└── Consumer C
```

This team is called a **Consumer Group**.

### Definition

> **A Consumer Group is a collection of consumers that work together to consume a topic in parallel.**

# Subtopic 3 – How Kafka Assigns Partitions

Suppose

```text
orders

├── P0
├── P1
├── P2
```

Consumers:

```text
Consumer A

Consumer B
```

Kafka assigns:

```text
Consumer A

↓

P0

P2
```

```text
Consumer B

↓

P1
```

Notice:

Kafka decides the assignment.

You don't manually assign partitions in the common case.

---

# Subtopic 4 – Rules of Consumer Groups ⭐⭐⭐

## Rule 1

One partition is assigned to only **one consumer** within the same consumer group.

Correct:

```text
P0 → Consumer A

P1 → Consumer B
```

Wrong:

```text
P0 → Consumer A

P0 → Consumer B
```

That would cause duplicate processing.

---

## Rule 2

One consumer **can** consume multiple partitions.

Example:

```text
Consumer A

↓

P0

P2
```

Perfectly valid.

---

## Rule 3

A partition cannot be shared by two consumers in the same group.

Kafka never allows this.

---

# Subtopic 5 – Scaling

Initially:

```text
inventory-group

Consumer A
```

Later, traffic increases.

You start:

```text
Consumer B
```

Now Kafka redistributes the work.

Instead of one consumer doing everything,

both consumers process events in parallel.

This is called **horizontal scaling**.

# Subtopic 6 – Common Scenarios

## Scenario 1

### 3 Partitions, 3 Consumers

```text
P0 → Consumer A

P1 → Consumer B

P2 → Consumer C
```

Perfect balance.

---

## Scenario 2

### 3 Partitions, 2 Consumers

```text
Consumer A

↓

P0

P2
```

```text
Consumer B

↓

P1
```

One consumer owns two partitions.

Valid.

---

## Scenario 3

### 3 Partitions, 1 Consumer

```text
Consumer A

↓

P0

P1

P2
```

Also valid.

---

## Scenario 4 ⭐⭐⭐

### 3 Partitions, 5 Consumers

```text
P0 → Consumer A

P1 → Consumer B

P2 → Consumer C

Consumer D → Idle

Consumer E → Idle
```

Kafka cannot assign more than one consumer to the same partition within a group.

So extra consumers simply wait.

# Summary

```text
Consumer Group

↓

Consumers work as a team

↓

Kafka assigns partitions

↓

One partition → One consumer

↓

One consumer → Multiple partitions (possible)

↓

More consumers = Better parallel processing
```

---

# Remember

* Consumer Group = Team of consumers.
* Consumers in the same group share the work.
* Kafka automatically assigns partitions.
* One partition belongs to only one consumer in a group.
* One consumer may own multiple partitions.
* If consumers > partitions, extra consumers remain idle.
* If partitions > consumers, some consumers handle multiple partitions.

---
Very good questions. Let's answer them one by one.

---

# 1. Do we need to create Consumer Groups?

**Yes.**

As developers, **we decide the group name**.

For example, in Spring Boot:

```properties
spring.kafka.consumer.group-id=inventory-group
```

or

```java
@KafkaListener(
    topics = "orders",
    groupId = "inventory-group"
)
```

When your application starts:

```text
Inventory Service
        │
group.id = inventory-group
        │
        ▼
Kafka creates the group if it doesn't already exist.
```

So you **don't create it manually in Kafka**. You simply provide a `group.id`, and Kafka manages the group.

---

# 2. "We don't need to think about the rules because Kafka assigns partitions."

Not exactly.

Kafka **does** assign partitions automatically, but you still need to know the rules because they explain **what Kafka is allowed to do**.

For example:

### Rule 1

One partition cannot be assigned to two consumers in the same group.

Suppose you have:

```text
Partition 0
```

Can Kafka do this?

```text
Consumer A ← Partition 0

Consumer B ← Partition 0
```

**No.**

Kafka itself follows this rule.

---

### Rule 2

Can Kafka do this?

```text
Consumer A

↓

Partition 0

Partition 1
```

**Yes.**

This is also a rule that Kafka follows.

---

### Rule 3

Suppose you have:

```text
3 Partitions

5 Consumers
```

Can Kafka assign one partition to two consumers just because there are extra consumers?

**No.**

The extra consumers stay idle.

---

## So why learn the rules?

Think of it like learning Java.

You don't manually decide how the JVM allocates memory.

The JVM does it.

But you still learn:

* Heap
* Stack
* Garbage Collection

because understanding the rules helps you predict the behavior.

Kafka is the same.

You don't assign partitions manually in the common case, but you should know the rules Kafka follows when it assigns them.

---

### For our learning journey

We don't need to memorize all the rules separately.

Just remember these **two**, because you'll use them all the time:

1. ✅ **One partition is assigned to only one consumer within a consumer group.**
2. ✅ **One consumer can own multiple partitions.**

Everything else is a consequence of these two rules.
