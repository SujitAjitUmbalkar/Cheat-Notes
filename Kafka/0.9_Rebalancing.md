# Subtopic 1 – Why Rebalancing is Needed?

Suppose we have:

```text
orders Topic

├── Partition 0
├── Partition 1
├── Partition 2
```

Consumer Group:

```text
inventory-group

Consumer A

Consumer B
```

Kafka assigns:

```text
Consumer A

↓

Partition 0

Partition 2
```

```text
Consumer B

↓

Partition 1
```

Everything is working.

---

Now suppose Consumer B crashes.

```text
Consumer A ✅

Consumer B ❌
```

Question:

Who will read Partition 1 now?

Nobody.

New events keep coming into Partition 1.

They will never be processed.

Kafka cannot allow this.

So Kafka starts **Rebalancing**.

---

# Definition

> **Rebalancing is the process of redistributing partitions among the active consumers in a Consumer Group.**

Remember this definition.

---

# Subtopic 2 – When does Rebalancing happen?

Rebalancing happens whenever the consumers in a group change.

There are three common situations.

### Case 1 – New Consumer Joins

Initially

```text
Consumer Group

Consumer A
```

Later

```text
Consumer Group

Consumer A

Consumer B
```

Kafka redistributes the partitions.

---

### Case 2 – Consumer Leaves

Example:

```text
Consumer B

↓

Stopped
```

Kafka assigns its partitions to the remaining consumers.

---

### Case 3 – Consumer Crashes

```text
Consumer B

↓

Application Crash
```

Kafka detects that it is no longer alive.

Again, Kafka redistributes the partitions.

---

# Subtopic 3 – How Rebalancing Works

Suppose

```text
orders

P0

P1

P2
```

Initially

```text
Consumer A

↓

P0

P1

P2
```

Now Consumer B joins.

Kafka says:

> "Let's redistribute."

After rebalancing:

```text
Consumer A

↓

P0

P2
```

```text
Consumer B

↓

P1
```

Notice:

No developer writes code for this.

Kafka does it automatically.

---

# Subtopic 4 – What Happens During Rebalancing?

This is important.

During rebalancing,

Kafka temporarily pauses consumption.

Think of it like this:

```text
Current Processing

↓

Pause

↓

Redistribute Partitions

↓

Resume Processing
```

Why pause?

Imagine Consumer A is still processing Partition 1 while Kafka gives Partition 1 to Consumer B.

Now both process the same partition.

Wrong.

So Kafka first pauses, then reassigns, then resumes.

---

# Subtopic 5 – After Rebalancing

Suppose Consumer B crashed.

Before:

```text
Consumer A

↓

P0
```

```text
Consumer B

↓

P1

P2
```

After Kafka finishes rebalancing:

```text
Consumer A

↓

P0

P1

P2
```

Consumer A now owns all partitions.

Processing continues.

No manual work is required.

---

# Example

Suppose you have:

```text
3 Partitions

2 Consumers
```

Assignment:

```text
P0 → A

P1 → B

P2 → A
```

Now B crashes.

Kafka automatically changes it to

```text
P0 → A

P1 → A

P2 → A
```

No configuration changes are needed.

# Real-life Analogy

Imagine a warehouse.

Three workers are packing boxes.

```text
Worker A

Worker B

Worker C
```

Suddenly,

Worker B goes home.

Manager says:

```text
Worker A

Take some of B's boxes.

Worker C

Take the remaining boxes.
```

Nobody manually redistributes every box.

The manager does it.

Kafka is that manager.

# Summary

```text
Consumer Group Changes

        │

        ▼

Kafka Detects Change

        │

        ▼

Pause Consumption

        │

        ▼

Redistribute Partitions

        │

        ▼

Resume Consumption
```

---

# Remember

* Rebalancing happens **inside a Consumer Group**.
* Kafka automatically performs rebalancing.
* It occurs when:

  * A new consumer joins.
  * A consumer leaves.
  * A consumer crashes.
* Kafka temporarily pauses consumption.
* Partitions are reassigned to active consumers.
* Consumption then resumes.

---

## One important note

We are learning the **logical behavior** here. Modern Kafka clients support strategies that can reduce the amount of stopping during rebalancing (called *cooperative rebalancing*), but since your PDF is teaching the core idea, it's best to first understand the classic flow:

```text
Change in Consumer Group
        ↓
Rebalancing
        ↓
Partitions Reassigned
        ↓
Consumption Continues
```
